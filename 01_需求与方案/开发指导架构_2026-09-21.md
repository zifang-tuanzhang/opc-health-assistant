## 0. 前提：编排正确性标准（先审，再谈架构）

### 0.1 什么是"编排正确"——6 条验收线（从 Agent 行为角度）
编排层的作用 = 定义 Agent 收到指令后**会触发哪些行为**。所以"正确"的标准是：**Agent 的行为集合 = 赛题要求的行为集合，且每条行为都受"原则/工具/契约/护栏"约束，模型是行为主体、代码是行为边界。**

| # | 验收线 | 判法 |
|---|---|---|
| 1 | **行为闭环完整** | 一句话进来能走完"理解→(澄清)→检索→提取→生成→护栏→交付"全程，不缺环节 |
| 2 | **行为可观测** | 关键行为有留痕（retrieval_log 检索词/状态/来源；护栏打回记录），可追溯 |
| 3 | **模型是行为主体** | 凡"判断/组织/回答"由模型在原则下自主完成；代码里搜不到任何"事实结论/预设对话" |
| 4 | **边界行为明确** | 诊断/用药/紧急/费用/医保/交通/出诊/时效，每条有明确触发+处理，不矛盾 |
| 5 | **有自纠闭环** | 产出不合格能打回（反射式循环），检索失败能降级提示，不崩溃不卡死 |
| 6 | **每条规则可执行** | 编排里每条规则都能翻译成"代码/工具/提示词"三选一，无空口号 |

### 0.2 用 6 条标准审视当前编排层 → 结论
- ✅ 1 闭环：编排层第 2.3 控制循环已定义完整链路。
- ✅ 2 可观测：retrieval_log 已升为第一类公民；护栏打回留痕已入 2.4。
- ✅ 3 模型主体：第 3 节"可/不可硬编码边界"已划死，事实全部由模型产出。
- ✅ 4 边界明确：诊断/用药/紧急/费用/医保/交通/出诊硬约束/时效诚实均已列清单。
- ✅ 5 自纠闭环：反射式校验打回循环（Validator/Reflector/Loop）已入 2.4。
- ✅ 6 可执行：每条规则均落在"原则层/工具层/护栏层/契约"四者之一，无悬空口号。

**结论：当前编排层已达标 6 条验收线，可确认。** 唯一建议补的"最后一道保险"= 用 2~3 个真实场景把行为轨迹走一遍（dry-run），见 Step 0。

### 0.3 建议补充的"行为轨迹场景清单"（Step 0 用，兼作 M7 测试素材）
- 场景A：`昆明哪家医院有抗蛇毒血清？` → 应触发"检索+三态标注(目前可提供尚待核实)+来源+紧急安全提示"。
- 场景B：`昆医大附一院心内科主任医师出诊时间？` → 应触发"澄清院区+检索+出诊硬约束(不推断号源)"。
- 场景C：`我头疼该吃什么药？` → 应触发"边界拒答(不诊断不处方)+引导就医"。

## 1. 框架蓝图（7 模块 + 数据流）

数据流：用户 → **M1 接入层** → **M2 编排核心循环**（按需调 M3/M4）→ **M5 契约渲染** → **M6 前端** 返回用户；**M7 测试交付**横贯全程。

| 模块 | 职责 | 关键构成 |
|---|---|---|
| M1 接入层（前门服务） | 收请求、会话管理、限流、密钥服务端 | FastAPI `/chat` + session_id 隔离 |
| M2 编排核心循环 | 模型当控制器，驱动行为 | 意图→澄清→检索→提取→生成→多轮 |
| M3 工具能力层 | 真联网能力 | search / fetch / session / retrieval_log |
| M4 护栏层 | 兜底自纠 | Validator(R1~R13) / Reflector / Loop(N=2) |
| M5 输出契约与渲染 | 定结构、渲染卡片 | 4段式 schema + 前端渲染 |
| M6 前端交互 | 用户可见 + 小程序接口 | Web 页 + 模拟调用标注 |
| M7 测试与交付 | 证明可用 | 8组测试 + 真实性证据 + 部署包 |

## 2. 三层拆分（业务模块 → 业务单元 → 逻辑规则）

### 2.1 M2 编排核心循环 → 6 个业务单元
| 单元 | 逻辑规则（L3） |
|---|---|
| U2.1 意图解析 | 识别 地区/医院/科室/资源/职称/日期；不含事实、只做槽位抽取 |
| U2.2 条件澄清 | 缺城市/院区/科室/日期 → 主动反问；不得替用户脑补 |
| U2.3 检索规划 | 优先官网/卫健委；构造检索词；同名院区消歧 |
| U2.4 事实提取 | 从来源提取事实+链接+时间+来源性质；三态标注；冲突标出 |
| U2.5 生成 | 按4段式schema；模型自主组织；不编造；空字段标"未查到/待核实" |
| U2.6 多轮承接 | 上下文记忆；会话隔离；可重置 |

### 2.2 M4 护栏层 → 3 个业务单元
| 单元 | 逻辑规则（L3） |
|---|---|
| U4.1 Validator | R1~R8 校验（结构/来源必填/来源可达/边界拒答/紧急120/禁断言/空字段诚实/检索真实性），只查左侧不查事实。**后续追加：R9 易变资源三态、R10 院区纪律、R11 同名医院/院区消歧一致性、R12 多来源冲突主动提示、R13 来源可追溯（防间接提示注入）、以及「澄清轮豁免」（`clarify=True` 时 R1/R7 豁免——澄清轮本就没有条件与结果；不豁免编造，2026-09-21）** |
| U4.2 Reflector | violations+hints 编码回灌 messages，模型重组织语言（不重新检索） |
| U4.3 Loop Controller | 最多打回 N=2；每轮留痕；超限降级输出（带⚠️提示）仍交付 |

### 2.3 M5 输出契约 → 逻辑规则
- 4段式：查询条件 / 查询结果[] / 信息依据[] / 使用提示[]。
- 每条结果强制 `source{title,url,来源性质,更新时间?,查询时间}` + `信息状态三态`。
- 检索过程 `retrieval_log[]` 独立展示，不混入答案。

## 3. 开发顺序（依赖优先，先做被依赖的）

| 步骤 | 做哪个模块 | 为什么先做 |
|---|---|---|
| Step 0 | 行为轨迹场景清单（dry-run） | 编排正确性的最后一道保险，兼作 M7 测试素材 |
| Step 1 | M5 输出契约 | 地基，所有模块都依赖它的数据结构 |
| Step 2 | M1 接入层骨架 | 先跑通能收发的空壳（/chat + 会话隔离） |
| Step 3 | M3 工具层 | 真联网，让 search/fetch/session/log 可用 |
| Step 4 | M2 编排循环 | 模型活起来，走通 意图→澄清→检索→生成 |
| Step 5 | M4 护栏层 | 兜底自纠，闭环 |
| Step 6 | M6 前端渲染 + 小程序接口 | 用户可见、可演示 |
| Step 7 | M7 测试8组 + 真实性证据 + 部署包 | 交付证明 |

> 顺序铁律：契约(Step1)→骨架(Step2)→工具(Step3)→循环(Step4)→护栏(Step5)→前端(Step6)→测试交付(Step7)，每步依赖前一步，不跳步。

### 5.2 与实现的偏差（已确认，不再视为矛盾）
- **M5 契约结构**：落地为**扁平 4 段式**（`query_condition / query_results / info_basis / usage_tips`），
  而非本文档 §2.3 曾提的嵌套"医院→医生→出诊"结构。原因：顶层扁平更适合模型稳定产出与前端/小程序直读；
  医生/出诊等细节由模型写在 `description` 内，结构仍受 R2/R6/R7 约束。
- **M4 护栏层**：实际落地 `src/guardrails.py`（Validator + Reflector）+ `src/orchestrator.py`（Loop Controller），
  与 §2.2 的 U4.1~U4.3 一一对应；R3（来源可达）**默认关闭**（原因见 `护栏层_2026-09-21.md` §5.2）。
- **M3 工具层**：已落 `search`（免密钥多后端：360 搜索桌面/移动 + 搜狗）/ `session` / `retrieval_log`；
  **`fetch(url)` 未实现**——是否补做待项目负责人拍板（影响进阶1 的交叉核验深度）。
