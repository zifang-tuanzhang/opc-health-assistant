# 密钥子系统设计说明

> 作品名称：AI 医院资源查询与便民就医助手
> 文档版本：2026-09-24 ｜ 状态：已完成并端到端验证

---

## 一、设计目标

产品需求可归纳为五点：把代码取到本地后，**只需点击「添加密钥」即可使用**，不需要翻找文件；密钥**不随项目一起存放**；环境依赖在项目目录内**形成闭环**（不依赖下载，避免下载失败）；**启动器能够拉起整个项目**（后端与前端）；命名使用**中文**。

逐条对齐的设计目标：

| 设计目标 | 落地方式 |
|---|---|
| 使用者无需翻找文件即可添加密钥 | Web「添加密钥」弹窗 + 预设厂商下拉 + 粘贴即连 |
| 密钥不随项目存放 | 密钥库位于项目外部 `%USERPROFILE%\.opc_health\keys.json`，版本库与 ZIP 均不包含 |
| 环境依赖在目录内闭环 | `wheels/` 内置离线安装包（cp311 / 312 / 313 win_amd64）；启动器优先以 `--no-index` 离线安装 |
| 启动器拉起整个项目 | `启动项目.py` + `启动项目.bat`（中文命名）：建虚拟环境 → 离线装依赖 → 启动后端 → 打开浏览器 |
| 配置成本最小 | 检索使用**免密钥**的公开检索（360 搜索 + 搜狗，详见 §2.5），使用者只需 **1 个模型密钥**即可端到端跑通 |

**结论：五项设计目标全部达成。** 以下给出设计、文件清单、使用流程与验证证据。

## 二、设计决策

### 2.1 预设厂商清单（随源码提供，不含任何密钥）

- 文件：`02_源码/keys/providers.preset.json`
- 内容：13 个主流国内厂商（DeepSeek / 通义千问 / 智谱 / 豆包 / 混元 / Kimi / MiniMax / 千帆 / SiliconFlow / StepFun / 星火）+ OpenAI 兼容网关 / 本地 Ollama。
- 每个厂商只存**配置元数据**：`vendor`（中文名）/ `base_url`（网关地址）/ `default_model` / `homepage` / `wire: openai` / `auth: bearer`。**不存密钥值**。
- 设计理由：国内厂商普遍提供 OpenAI 兼容网关（与 OpenAI 接口规范一致），后端只需一套 `openai` SDK（软件开发工具包），按 `base_url` 切换。使用者在下拉框中即可选择，无需手工填写网关地址。

### 2.2 外部密钥库（项目外、版本库不含、自动扫描）

- 代码：`02_源码/src/keystore.py`
- 固定位置：`%USERPROFILE%\.opc_health\keys.json`。
- **约束**：密钥只读写该外部文件，绝不写回项目内任何位置；即使将整个项目打包为 ZIP 分发，密钥也不会随包流出。
- 后端在每次启动与每次请求时都会**自动扫描**该固定位置，存在有效密钥即直接连接。
- 提供函数：`is_configured()` / `get_active()` / `upsert_provider()` / `set_active()` / `list_configured()` / `store_path()`（对外暴露库路径，便于查看）。

### 2.3 Web 添加密钥页与自动扫描路由（连接成功才写入）

- 代码：`02_源码/src/keys_routes.py` + `02_源码/static/index.html`
- 路由（前缀 `/api/keys`）：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/providers` | 返回「添加密钥」界面的下拉清单（不含密钥值） |
| `GET` | `/status` | 返回后端自动扫描外部密钥库的结果（是否已配置、库位置） |
| `POST` | `/add` | 选择厂商并粘贴密钥 → **真实连接校验一次**（`test_connection`，`max_tokens=1` 的极小调用）→ 成功才写入外部库；失败返回 `400` 并说明原因，**不写入** |

- 前端：暗色主题聊天界面，`index.html` 内包含「添加密钥」弹窗（厂商下拉 + 模型名 + 密钥输入框 + 状态横幅），全程不涉及文件操作。

### 2.4 启动器闭环（中文命名，一键拉起）

- 文件：`启动项目.py`（主逻辑）+ `启动项目.bat`（纯 ASCII 入口，避免 GBK（中文编码）乱码导致进程提前退出）
- 流程：

1. `find_python()` 查找 3.10 及以上的 Python 解释器；
2. `bootstrap_venv()` 创建 `.venv`，优先以 `pip install --no-index --find-links wheels/` **离线安装**（无网络亦可），失败才回退在线安装；
3. `start_backend()` 通过 uvicorn（ASGI 服务器）启动 `src.server:app`，监听 `127.0.0.1:8137`；
4. `wait_ready()` 等待健康探测通过；
5. `webbrowser.open()` 自动打开浏览器指向交互界面。

- 命名：全程中文（`启动项目`），在文件管理器中双击 `.bat` 即可运行。

### 2.5 免密钥检索（使用者只需 1 个模型密钥）

- 代码：`02_源码/src/search.py`
- 真实联网检索使用 360 搜索（桌面版 + 移动版）与搜狗搜索的公开页面，**不需要任何 API 密钥**。
- 价值：使用者只需填写 1 个模型密钥即可获得完整回答，检索环节零密钥也能真实联网，配置成本显著降低；同时检索结果真实可核验，符合「真实联网、不硬编码」的要求。
- 失败处理：检索失败时静默返回空列表，不编造内容。

### 2.6 依赖闭环（随仓库提供的离线安装包）

- 目录：`wheels/`（51 个包，约 18 MB，覆盖 Python 3.10–3.13 win_amd64）
- 包含：fastapi / uvicorn / pydantic v2 / openai / httpx / python-dotenv 等。
- 已实测：新建空白 `.venv_test` 后执行 `pip install --no-index --find-links wheels/` → 全部安装成功，`openai 3.16.2` 确认可用。**断网环境同样可以完成安装。**
- `.gitignore` 排除 `.venv/` / `.env` / `*.local.json`，但**保留 `wheels/`**（属交付闭环的组成部分）。

## 三、参考的工程做法

本密钥子系统在实现前参考了同类密钥管理工具的公开工程做法（仅作只读参考，**未复用其代码**，业务逻辑从零自研）：

| 参考做法 | 本作品的落地 |
|---|---|
| 预设厂商注册表随源码提供、不含密钥 | `02_源码/keys/providers.preset.json`（13 家厂商清单为自行编写） |
| 密钥库存放于项目外部 | `keystore.py` 存于 `%USERPROFILE%\.opc_health\keys.json`（路径自行确定） |
| 启动器 `.bat` 使用 ASCII 编码避免 GBK 乱码 | `启动项目.bat` 为纯 ASCII 入口，转调 `启动项目.py` |

**未采用的部分**：终端式交互界面与重量级密钥管理后台。本项目以 Web 弹窗 + 极简启动器实现同等目标，更符合「零配置上手」的定位。

## 四、使用流程（3 步）

```
1. 双击「启动项目.bat」 → 自动建虚拟环境 + 离线装依赖 + 启动后端 + 打开浏览器
2. 浏览器打开后，右上角入口显示「未配置模型密钥」（首次进入会自动弹出提示指出位置）→ 点击该入口
3. 选择厂商（下拉框）→ 粘贴密钥 → 确认 → 后端执行真实连接校验，成功后即可开始提问
```

- 若密钥无效：弹窗明确提示「连接失败：xxx」，**不写入**，可重试。
- 密钥位置：界面 `/api/keys/status` 会显示库路径，可查看、可手动清除。

### 5.2 实时连接校验抽检（真实网络）

- 使用无效密钥调用 `test_connection` 至 DeepSeek 真实网关 → 返回 `ok=False | 连接失败：AuthenticationError: 401 ...invalid`。
- 结论：`/api/keys/add` 路径会拒绝无效密钥、返回清晰错误、不崩溃、不写入。

### 5.3 离线依赖实测

- 空白 `.venv_test` + `pip install --no-index --find-links wheels/` → 全部安装成功，`openai 3.16.2` / `fastapi 0.141.1` / `uvicorn 0.53.0` 确认。

### 5.4 真实密钥端到端联调（通义千问）

- 通过架构入口将密钥写入外部密钥库（`%USERPROFILE%\.opc_health\keys.json`），激活 `qwen / qwen-turbo`。
- 连接校验：`test_connection` 至 DashScope（阿里云百炼）兼容网关 → `ok=True | 连接成功`。证明密钥有效、网关正确、校验逻辑正确。
- 端到端 `run_turn("昆明哪家三甲医院有心血管内科？")` → `ok=True, mode=agent, degraded=False`，产出真实四段式结果（region=昆明）。
- 关于供应商兼容性的两点结论：

  1. 端到端链路已跑通，编排逻辑正确。若出现无法连接的情况，优先排查密钥失效、模型名错误、`base_url` 错误或网络问题，而非核心逻辑——因为连接与编排路径是与供应商无关的通用实现。
  2. 更换其他供应商同样可行。所有厂商使用同一套 OpenAI 兼容客户端与 `test_connection` 通用校验；千问跑通即说明该通用路径正确。某厂商无法连接通常源于该厂商预设的 `base_url` 或模型名配置错误，或该厂商密钥与网关本身的问题。

- **联调中发现的真实问题及修复**：早期检索层依赖 DuckDuckGo，在本地网络环境下不可达（SSL 超时），Bing 与百度返回反爬降级页，导致「真实联网检索」一度取不到真实结果；且原编排逻辑在检索为空时仍会生成带 URL 的来源（等同以预设内容冒充动态查询）。已修复两点：① 检索层改为 360 搜索（桌面版 / 移动版）+ 搜狗，实测可取到真实文章级来源；② 检索为空时编排层显式告知模型「未检索到结果」，模型须返回空结果与空来源，并说明「暂未查到可核验信息」，**不编造来源**（详见 §5.5 与 §六.1）。

### 5.5 检索为空时不编造（验证）

- 同环境再次执行 `run_turn`（检索仍为空）→ `query_results=0, info_basis=0`，`usage_tips` 为「暂未查到可核验的联网信息，请以医院官方渠道为准」，**未生成任何来源**。
- 该行为与检索后端无关：无论使用者所在网络能否访问搜索引擎，只要检索为空，系统即明确返回未查到，不编造来源。

## 六、已知局限

1. **真实 Agent 循环已通过真实密钥端到端验证**（模型调用 → 四段式生成），且**真实联网检索已取到真实医院来源**（见 `03_测试记录/真实性证据_2026-09-21.md`：360 搜索实网返回文章级 URL）。**仍存在的边界**：免密钥后端均为第三方公开页面，持续高频请求下会被风控（本机自测中三个后端先后触发过，见 `检索层风控与加固_2026-09-21.md`）；正常使用量级不受影响，极端情况会走「检索为空 → 不编造」路径（§5.5）。如需进一步保障，可在密钥库中增加付费搜索类供应商（SerpAPI / Brave Search / Bing Web Search），本函数签名不变，属可选增强。
2. **反射式打回循环（Validator / Reflector / LoopController，N = 2）已接入并实测通过**：`orchestrator.py` 内已包含完整的「打回—重生成」循环（最多 N = 2 轮；仍不通过则降级交付并附 ⚠️ 提示，不崩溃）；护栏层测试中包含 `[PASS] N6 解析失败可打回 note=护栏打回 1 轮后通过`。
3. **`wheels/` 仅含 Windows（win_amd64）轮子**：按 Windows 环境交付；若需在 macOS / Linux 运行，需补充对应平台轮子或改用在线安装（启动器已包含在线回退）。
