## 〇、赛题条款分层（读本文档前先分清层级）

赛题原文共六节，**性质不是同一类**，不要混为一谈：

| 赛题章节 | 性质 | 约束力 | 本文档对应节 |
|---|---|---|---|
| 二、赛题核心目标 | 目标（方向性） | 指引，不逐条验收 | 第三节 |
| 三、基础需求 1~7 | **功能需求**（必做） | 原文：「参赛作品应**全部实现**」 | 第四节 |
| 四、进阶需求 1~4 | **功能需求**（选做） | 原文：「选手**可按时间和技术条件选择**完成」 | 第九节 |
| 五、信息来源与素材说明 | **边界说明**（不含功能） | 约束"数据从哪来、不能声称什么" | 第五节 §5.1 |
| 六、技术约束与提交要求 | **红线 + 验收方式 + 交付清单** | 约束"不许做什么、怎么被验收、交什么" | 第五节 §5.2 |

**要点**：第五、六节**不是功能需求，也不是进阶需求**——它们是「边界/红线/交付清单」。
判断某条要不要"做功能"时，只看第三、四节；判断某条会不会"踩线/漏交"时，才看第五、六节。

## 一、30 秒跑起来（访问方式 + 启动步骤）

```
1. 解压交付包（ZIP 压缩包格式）到任意目录
2. 双击  启动项目.bat
3. 浏览器自动打开  http://127.0.0.1:8137
4. 点右上角「模型密钥」入口（首次进入会自动弹出提示指出位置）→ 选一家厂商 → 粘贴你自己的模型 Key → 保存
5. 开始提问
```

- **不需要联网安装依赖**：交付包内已内置 51 个离线依赖轮子（wheel 格式的预编译安装包）。
- **不需要申请任何搜索接口**：检索全部走免密钥的公开搜索页面。
- **不填模型 Key 也能启动**：进入「待配置模式」——接口正常响应、页面正常打开，但**不发起检索、不调用模型**，直接提示「未配置模型密钥」并给出配置引导（`error_code=NEED_KEY`）。填入 Key 后立即恢复真实联网检索。
- 其它两条启动路径（容器 / 手动 Python）与排障见 `部署说明_2026-09-21.md`。

### 「15 分钟内启动」实测计时（赛题硬要求，非估算）

赛题要求：无法公网部署时，可提供本地一键运行包，**确保评审在 15 分钟内按说明启动**。
本作品不满足"公网部署"条件，走的就是本地一键运行包这条路径，因此该项**必须实测**。
实测方式：全新目录、**全程断网**（依赖从包内轮子离线安装）、逐环节计时。

| 环节 | 实测耗时 |
|---|---|
| ① 解压交付包 | 0.2 秒 |
| ② 创建虚拟环境（venv） | 4.5 秒 |
| ③ 离线安装 34 个依赖（不联网） | 18.8 秒 |
| ④ 启动服务到 `/health`（健康检查接口）可响应 | 1.7 秒 |
| **合计（含解压）** | **25.2 秒 ≈ 0.4 分钟** |

> **对赛题 15 分钟要求：余量约 14.6 分钟（97%）**。
> 说明：计时使用本机（Windows）实测值；换机器会因 CPU 与磁盘速度有差异，
> 但"离线装依赖 + 单进程启动"这条路径不含任何需要联网等待的环节，因此不存在网络波动带来的不确定性。
> 上述 25.2 秒为**服务可用**耗时；之后评审还需一步配置模型密钥（点右上角入口，粘贴自己申请的模型 Key），
> 这是交互动作而非等待过程。

## 二、演示范围、技术选型、依赖清单（赛题要求「注明模型、联网搜索工具及版本或服务名称」）

| 项 | 内容 |
|---|---|
| **演示地区** | **昆明市**（默认演示城市，可用 `OPC_DEMO_CITY` 改）。演示覆盖公立医院与具有可核验公开信息的民营医院 |

| **联网搜索工具** | **不依赖任何第三方搜索 SDK 或 API**。自研检索层直接请求公开搜索页面并解析，**默认 3 个后端**按顺序回退：`so360`（360 搜索桌面版）→ `mso360`（360 搜索移动版）→ `sogou`（搜狗搜索）。另有 `ddg`（DuckDuckGo，一款海外搜索引擎）保留在代码中但**默认不启用**——它在国内不可达，每次外呼要白等满超时（详见第六节末「检索总耗时预算」） |
| **Web 框架** | FastAPI（版本随离线轮子） + uvicorn（ASGI 服务器） |
| **HTTP 客户端** | httpx（用于检索层外呼） |
| **模型调用** | openai 官方 Python SDK（统一走 OpenAI 兼容接口，用 `base_url` 切换厂商） |
| **编排层** | **自研轻量编排层**（核心设计：**模型当控制器**——代码只定义结构、契约、工具与护栏，把「用哪个工具、怎么组织回答」交给模型）。**不使用** LangGraph（图式智能体框架）、**不使用** RAG（检索增强生成）或向量数据库 |
| **前端** | 单页原生 HTML + JavaScript（`02_源码/static/index.html`），无构建步骤 |

### 检索总耗时预算（`OPC_SEARCH_BUDGET_SECONDS`，默认 18 秒）

「多后端依次回退」这种设计有个容易被忽略的陷阱：**每个后端各自的超时，都会变成整体延迟的加数**——
后端越多，"更健壮"反而"更慢"，而且**慢得没有上界**。
本项目在自测中真实踩到过：默认列表里有一个**国内不可达**的后端（DuckDuckGo），
每次外呼要白等满 12 秒超时，遇上其余后端被风控时，一次提问的端到端响应达到 **62.9 秒**——
使用者会直接把"慢"读成"坏了"。

因此检索层加了一条**总耗时预算**：

- 单次检索的**外呼总耗时**不超过该预算（默认 18 秒）；
- **第一个后端保证至少跑一次**（不因预算把检索整个跳过，避免"假降级"）；
- 此后预算耗尽即**停止尝试后续后端**，直接返回已有结果；
- 每次外呼的超时按**剩余预算**收缩，不会用 12 秒去等一个只剩 2 秒的窗口。

**效果**：修复前 62.86 秒 → 修复后 **8.88 秒**（同一台机器、同一查询、同样处于搜索引擎风控中）。
输出内容不变（仍是空结果 + 诚实降级 + 可点击的手动检索入口，**零编造**）。
细节与实测证据见 `03_测试记录/检索层风控与加固_2026-09-21.md` 加固 8。

## 七、缓存与存储及其更新策略（赛题明确要求说明）

| 存储 | 位置 | 用途 | 更新/失效策略 |
|---|---|---|---|
| 检索结果缓存 | **进程内内存** | 同一查询在短时间内复用检索结果，减少对外请求（降低触发搜索引擎风控的概率） | TTL（存活时间）**600 秒**；**只缓存非空结果**（空结果不缓存，避免把一次失败固定下来）；进程重启即清空 |
| 模型应答缓存 | 进程内内存 | 相同（模型, 消息, 参数）的请求在 TTL 内直接复用 | TTL **86400 秒**；每日 token 预算上限 1,000,000 |
| 会话存储 | 进程内内存 | 多轮上下文（默认保留最近 12 轮） | 可 `POST /reset` 主动清空；进程重启即清空 |
| 密钥库 | 项目目录之外（`%USERPROFILE%\.opc_health\keys.json`） | 存放评审自填的模型密钥 | 不随交付包分发；不写入任何日志 |
| 检索样本快照 | `02_源码/tests/fixtures/`（**仅测试用**） | 离线验证解析器与风控页识别，避免测试依赖网络状态 | 静态证物，附采集脚本与 SHA256 校验值，可随时重采 |

> 以上均为**进程内内存**实现，**未使用数据库或 Redis 等外部存储**，适用于单实例演示场景。缓存**只用于复用检索结果与应答**，**不构成任何"预录答案"**——缓存内容是当次真实检索的产物，且空结果不入缓存。
