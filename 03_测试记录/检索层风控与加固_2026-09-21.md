# 检索层风控事故与加固记录

> 日期：2026-09-21
> 对象：检索层 `02_源码/src/search.py`（免密钥多后端瀑布检索）
> 触发方式：本机对抗测试高频检索
> 结论：**已定位真实红线风险并加固；加固结果离线可复跑验证（61/61）**

---

## 一、事故现象

在做第二轮对抗测试期间，检索层突然整体失效：

| 观测项 | 数值 |
|---|---|
| 受控测量（同一查询连测 8 次） | **成功 0 / 8 = 0%** |
| 单次耗时 | 1.7 秒 → 5.7 秒（显著变慢） |
| 返回内容 | 非空 HTML，但**解析出 0 条结果** |

初看像"解析器坏了"。实际不是。

---

## 二、诊断过程（四步定位）

### 第 1 步：排除"解析器坏了"

用固定查询词直接取回原始 HTML，打印结构特征：

```
360搜索 HTTP 200 ｜ {'含res-list': 0, '含h3': 0, '含验证/安全提示': 2, '含data-mdurl': 0, '长度': 9837}
正文开头: …<title>访问异常页面</title>
```

**HTTP 状态码是 200（成功）**，但页面正文是——**「访问异常页面」**。

### 第 2 步：确认不是个例

| 后端 | HTTP | 页面标题 | 判定 |
|---|---|---|---|
| 360搜索 | 200 | 访问异常页面 | 已触发风控 |
| 百度 | 200 | 百度安全验证 | 已触发风控 |
| DuckDuckGo lite | 202 | （无内容） | 本环境不可用 |
| 搜狗 | 200 | 昆明哪家医院有抗蛇毒血清 - 搜狗搜索 | ✅ 正常（会间歇降级） |

**四个免密钥后端里三个不可用**，且都是"返回 HTTP 200 但内容是风控页"。

### 第 3 步：定位根因

通过本机代理换出口 IP 复测：百度、360 仍然被拦（同一 IP 累计请求量过大触发风控，与本机指纹相关）。

**根因：本机在短时间内发出大量检索请求（我自己的对抗测试造成的），触发了搜索引擎的风控机制。**
这是**测试环境污染**，不是产品缺陷——真实使用者一次咨询只会发几条查询，不会触发。

### 第 4 步：找出真正的红线风险（这一步是本次事故最大的收获）

风控页**返回的是 HTTP 200**。如果解析器把它当成正常结果页解析，会有两种后果：

| 后果 | 严重性 |
|---|---|
| 解析出 0 条 → 走诚实降级"暂未查到" | 可接受（功能降级） |
| 把风控页里的文字当成"搜索结果标题/来源" | **严重**：产出**编造来源**，直接违反赛题约束 |

所以这不只是一个"稳定性"问题，是一个**红线防护漏洞**。

---

## 三、加固内容（四项）

### 加固 1：风控页识别（红线防护，最关键）

新增 `_is_block_page()`：所有外呼统一过一道检测，**识别到风控页即视为该后端失败**（返回空串 → 自动切下一个后端 → 全失败则走诚实降级）。

只查页面 `<title>`，不扫正文——因为正常新闻正文里出现"安全验证"是常见的，扫正文会大面积误杀正常结果。

```python
_BLOCK_TITLE_MARKERS = ("安全验证", "访问异常", "验证码", "人机验证",
                        "请稍后再试", "拒绝访问", "unusual traffic",
                        "captcha", "forbidden")
```

**取舍说明（有意为之）**：标题命中即判风控页。
- 漏判的代价：把验证页当搜索结果 → 产出编造来源 → **违反约束，不可接受**；
- 误判的代价：只是多切一个后端/多一次降级 → **无害**。
代价不对称，故取"宁严勿漏"。

### 加固 2：新增搜狗后端（可用冗余）

| 后端 | 来源 URL 粒度 | 说明 |
|---|---|---|
| `so360`（第一） | **文章级**（原文直链） | 首选 |
| `sogou`（第二，**新增**） | **域名级**（`<cite>` 真实站点地址 + 发布日期） | 作为 360 不可用时的第二兜底 |
| `ddg`（第三） | 文章级 | 国内常不可用 |

搜狗结果块的 `<h3>` 内是搜狗跳转链（`/link?url=…`），实测该地址返回 HTTP 200 的 HTML 跳转页（不是 302），解析它需要每条结果多发一次请求，性价比低且加重风控，**故不用**；改用 `<cite>` 内的真实站点地址。拿不到真实地址的条目不收录（宁少不假）。

> 注：搜狗 URL 是域名级，比 360 的文章级弱一档（点进去是站点首页而非具体页面）。因此 **搜狗排在 360 之后**，只在 360 不可用时接手。这是一次有意识的能力让步：**宁可来源粒度弱一点，也不能没有来源**。

### 加固 3：结果缓存（10 分钟 TTL）

同一查询 10 分钟内直接复用，不再打对方服务器。
- 降低触发风控概率；
- 演示场景里连续追问同一话题时响应更稳更快。
- **只缓存非空结果**（空结果要允许恢复，不能被缓存钉死）；全部 fail-open。

### 加固 4：出站节流（最小间隔 1 秒）

两次外呼之间强制间隔 ≥1 秒，避免并发把自己送进风控。

### 加固 5：产品化降级（手动检索入口，代码兜底）

即使三重加固都做完，"三后端同时限流"仍然可能发生。此时若只回一句"暂未查到"，使用者会以为**检索功能坏了**。

所以在降级时由**代码**补一条可点击的**手动检索入口**（不依赖模型是否听话——模型给的 `usage_tips` 可能只有干巴巴一句）：

```
当次联网检索服务可能被搜索引擎限流，暂未取得可核验结果；
你可以点这里自行检索同一批引擎：
  360搜索：https://www.so.com/s?q=<已编码查询词> ｜
  搜狗搜索：https://www.sogou.com/web?query=<已编码查询词>
请以医院官方渠道信息为准。
```

设计红线（务必守住）：这条提示里放的是**搜索引擎的查询地址**，**不是"来源"**——它不冒充检索结果、不进 `query_results`。测试里专门有一条断言防止它被误当作事实来源。

> 这与"三态标注由护栏强制、不交给模型"是同一套思路：**该由代码保证的事，就不要指望模型自觉。**

### 加固 6（第二轮补做）：同引擎「移动版入口」作为抗限流冗余

**动因（继续实测）**：做完前五项加固后，本机再次被限流。此时逐后端单独试探，出现一个关键现象：

| 入口 | 当时表现 |
|---|---|
| `www.so.com/s`（360 桌面版） | HTTP 200，但 `<title>` 是「访问异常页面」→ 判风控，返回空 |
| `m.so.com/s`（360 **移动版**） | HTTP 200，正常结果页，**同一分钟内仍可出结果** |

即：**同一引擎的桌面版与移动版是不同入口、各有各的限流额度**。且移动版结果块里的 `data-pcurl` 直接给出
**文章级原文直链**（如 `news.qq.com/rain/a/20250612A01YGT00`），来源粒度与桌面版同级。

> ⚠️ **重要更正（本机继续实测所得，必须如实标注）**：上表的"桌面版被风控、移动版仍可用"成立，但
> **不代表移动版免疫**。做完加固 6 之后，本机继续高频自测，最终出现**桌面版与移动版同时返回
> 「访问异常页面」**（两者紧挨着先后被封），冷却 180 秒后仍未恢复（属 IP 级、以十分钟计的封禁）。
> 因此准确定位是：**移动版把"被挡住"的请求量上限抬高了一层，并多给一次回退机会，但不是免疫。**
> 正常使用（一次若干问）属中等量级，落在"两个入口不会同时封"的区间内。

**做法**：把 `mso360` 注册为第 2 个后端（紧跟 `so360` 之后、排在域名级的 `sogou` 之前），默认顺序变为
`so360 → mso360 → sogou`（ddg 已移出默认列表，见加固 8）。解析器 `_parse_mso360` 仍遵守原有红线：**拿不到真实 URL 的条目一律丢弃**，
并把引擎自身的模块卡（标题以「_相关医院」结尾、链接指回 `m.so.com`）用 `_is_engine_url` 剔除。

**效果（同一分钟内前后对照，同一查询「昆明 抗蛇毒血清 医院」）**：

| | 加固 6 之前 | 加固 6 之后 |
|---|---|---|
| 命中条数 | **0 条**（桌面版风控 + 搜狗 403） | **4 条文章级来源**（走移动版） |
| 耗时 | — | 2.60s |

**刻意排除的两个候选**（也一并留痕，避免以后重复试错）：

| 候选 | 实测 | 为什么不用 |
|---|---|---|
| `www.bing.com`（带 `mkt=zh-CN`） | HTTP 200、标题含查询词，但结果**全被放宽**（问"昆明 抗蛇毒血清 医院"只返回"昆明"旅游/百科） | 会产出**答非所问的"来源"**——比诚实降级更危险（等于另一种编造） |
| `www.baidu.com/s` | HTTP 200、标题切题 | 结果链接全是 `baidu.com/link?url=` 跳转链（同搜狗的跳转问题，需为**每条**结果再发一次请求），性价比低且抬高限流概率 |

> 结论：**"能返回 200"不等于"能当来源"**。这一条正是本项目风控页识别（加固 1）的同源教训——
> 判断一个后端能不能用时，看的是**解析出来的东西是否真的切题、真的有原文直链**，不是看状态码。

### 加固 7（第三轮实测补记）：风控改以「302 重定向」形式出现时的红线复验

**为什么要补这一条**：本机连续高频自测后，三后端同时 0 命中。
此时**必须先排除"是不是解析器坏了"**——若把代码缺陷误判成"环境被限流"，
就会带着坏代码交付，而且理由看起来还很正当。

**取证方法：看响应本身，不看"0 条"这个结果**（"0 条"对两种原因是同一个表现，不能当判据）：

| 后端 | 观测 | 判定 |
|---|---|---|
| `www.so.com/s` | HTTP **302** → `http://qcaptcha.so.com/?ret=…`（360 验证码页） | 风控 |
| `m.so.com/s` | HTTP **302** → 同上 | 风控 |
| `www.sogou.com/web` | HTTP **302** → `http://www.sogou.com/antispider/?…`（搜狗反爬页） | 风控 |

结论：**是风控，不是解析器故障**。判据是**重定向目标主机名**（`qcaptcha` / `antispider`），
不是"结果条数为 0"。

**红线复验（关键）**：生产代码是 `follow_redirects=True`（跟随重定向），
所以真正要问的是——**跟过去的那一页，会不会被当结果解析？** 连测 4 次：

```
#1 ~ #4   HTTP 200   9837 B   title='访问异常页面'   判风控=True   解析=跳过
```

**4/4 全部被 `_is_block_page` 拦下**（标题命中"访问异常"）→ 不解析、不编造。

补一层兜底推理：即便某次风控页**标题"长得正常"而漏判**，该页**不含结果块结构**，
`_parse_so360` 只会得到 0 条 —— **仍然不会编造来源**。
（这一点也与加固 1 的取舍说明一致：误判无害、漏判才是红线。）

**当次对用户说的话**（`orchestrator._manual_search_tip`，由代码兜底写入，不依赖模型听话）：

> 当次联网检索服务**可能**被搜索引擎限流，暂未取得可核验结果；
> 你可以点这里自行检索同一批引擎：360搜索：… ｜ 搜狗搜索：…。请以医院官方渠道信息为准。

用"**可能**"同时覆盖"被限流"与"确实没查到"两种原因——**两种情形下都不撒谎**。

**仍未解决**：截图空档。本轮实测确认本机 IP 仍处风控，故
`G2 / G4 / G5` 三组的**真机截图依旧采不到**（强拍只能拍到降级态、拍不到该组要证明的东西）
→ **宁可不拍，也不拍一张不证明结论的图**。

### 加固 8（第四轮实测补记）：默认移除国内不可达后端 + 检索总耗时预算

**触发**：本轮做端到端实跑体检时，`POST /chat` 实测**耗时 62.86 秒**才返回。
内容是对的（诚实降级、零编造），但**62 秒的等待在使用者眼里等于「系统卡死」**——
赛题《基础需求7·基础交互》明确要求「接口超时…均有明确提示」。

**根因（有独立证据，不是推测）**：
检索主函数是按「**后端 × 查询变体**」双层循环写的，**总耗时 = 所有外呼超时之和，没有上界**：

```
for name in SEARCH_BACKENDS:        # 每个后端
    for v in _query_variants(q):    # 每个变体（空格分词串 / 去空格连写）
        hits = fn(v, max_results, timeout)
```

而列表里的 `ddg`（DuckDuckGo）在国内网络**不可达**，每次外呼都要**白等满 12 秒超时**：

| 证据 | 实测值 |
|---|---|
| 单独探测 ddg 后端 | **24.7 秒**（2 个变体 × 12 秒，全部超时） |
| 外呼日志（uvicorn httpx 日志） | 确见 `duckduckgo` 请求被发出，且它在 so360/mso360/sogou 之后全部失败才轮到 |
| 修复前端到端 `/chat` | **62.86 秒** |

即：**在三个国内后端都被风控的情况下，唯一"兜底"的 ddg 反而贡献了整条链路里最长的一段纯等待**。

**加固动作（两处）**：

1. **默认后端列表移除 `ddg`** → `so360,mso360,sogou`。
   - 代码里仍**保留 `ddg` 的注册与解析器**，需要时用 `OPC_SEARCH_BACKENDS="so360,mso360,sogou,ddg"` 显式加回；
   - 理由：它是**海外**引擎，国内演示场景下它的期望收益为 0、期望成本 24 秒。

2. **新增检索总耗时预算 `SEARCH_BUDGET_SECONDS`（默认 18 秒）** ——这才是根本护栏：
   - 不管后端列表以后被配成什么，单次检索的**外呼总耗时有上界**；
   - 第一个后端**保证至少跑一次**（不因预算把检索整个跳过，避免"假降级"）；
   - 此后预算耗尽即停止尝试后续后端，直接返回已有结果；
   - 每次外呼的超时按**剩余预算**收缩（`min(timeout, 剩余)`），不会用 12 秒超时去打一个只剩 2 秒的窗口。

**复验结果（修复前 → 修复后）**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 端到端 `POST /chat` 耗时 | **62.86 秒** | **8.88 秒**（↓ 86%） |
| 外呼过的后端（日志实证） | so360 / mso360 / sogou / **ddg** | so360 / mso360 / sogou（**无 ddg**） |
| 输出正确性 | 空结果 + 诚实降级 + 手动检索入口 | 同上（**未编造，红线不变**） |
| 离线四套断言 | 110 项 | **115 项**（解析套件 56 → 61） |

新增 5 项断言，其中一项是**真跑的行为测试**（不是只断言配置存在）：
注入两个"慢后端"、把预算设成 1.2 秒 → 断言**只外呼 1 次、总耗时 < 1.6 秒**，
证明预算确实截断了外呼，而不是只写在配置里。

**这一条的经验（写给以后）**：
"多个后端依次回退"这种设计，**必须配一个总预算**。否则每个后端各自的超时都会变成
整体延迟的加数——后端越多，"更健壮"反而"更慢"，且慢得没有上界。

### 配套改动：解析器与网络解耦（可测性）

把检索层拆成 **外呼层 `_get()`** 与 **纯解析函数 `_parse_so360 / _parse_mso360 / _parse_sogou / _parse_ddg`**。这样解析器可以用真实页面样本做**离线确定性**验证——无论交付后引擎是否再次风控，测试都能稳定给出结论。

| 360 风控自动恢复后 | ✅ 返回 4 条**文章级**真实链接（新浪 / 今日头条 / 微博） |
| **加固 6 后：桌面版仍被风控时** | ✅ 瀑布切至**移动版**，同一查询从 **0 条 → 4 条文章级来源**（含 `news.qq.com` 原文直链 + 发布日期），耗时 2.60s |
| **加固 6 后：继续高频，两入口先后被封** | ⚠️ 桌面版与移动版**同时**返回「访问异常页面」；冷却 180s 未恢复。→ 如实定位：**提高上限，不是免疫** |

### 实机降级验证（限流现场）

加固后再次遇到三后端同时限流，用真实 HTTP 接口验证降级路径。实测返回（原文节选）：

```json
{
  "ok": true, "mode": "agent", "degraded": false,
  "retrieval_log": [{"action":"search","query":"昆明 抗蛇毒血清 医院","status":"empty","hit_count":0}],
  "output": {
    "query_results": [], "info_basis": [],
    "usage_tips": [
      "暂未查到可核验的联网信息，请以医院官方渠道为准",
      "当次联网检索服务可能被搜索引擎限流，暂未取得可核验结果；你可以点这里自行检索同一批引擎："
      "360搜索：https://www.so.com/s?q=%E6%98%86%E6%98%8E%20... ｜ "
      "搜狗搜索：https://www.sogou.com/web?query=%E6%98%86%E6%98%8E%20..."
    ]
  }
}
```

要点：**结果为空（零编造）**，但用户拿到了可点击的自助入口——使用者看到的是"产品降级"，不是"功能坏了"。

### 反面对照实验：重试能不能救回来？

限流时搜狗会在「正常页（584KB）」与「薄页（5.4KB，`<title>搜狗搜索</title>`）」之间切换。于是做了个直接实验——**同一查询连发 4 次**：

```
第1次:    5478字节 解析0条  title='搜狗搜索'
第2次:    5478字节 解析0条  title='搜狗搜索'
第3次:    5478字节 解析0条  title='搜狗搜索'
第4次:    5478字节 解析0条  title='搜狗搜索'
```

**结论：重试无效。** 薄页是一个**持续状态**（不是秒级抖动），所以：

> **本次刻意没有实现"失败自动重试"。** 依据是上面这个实验——重试只会白白增加对对方服务器的请求量（反而可能延长限流），并不会提高成功率。不加没有依据的功能。

（`_query_variants` 的"换措辞再试"保留，但它针对的是**引擎对措辞敏感**这一另一回事，不是用来对抗限流的；本作品不作出"它一定能提高命中率"的承诺。）

## 六、遗留风险与如实标注

| 风险 | 说明 | 处置 |
|---|---|---|
| **免密钥后端天然不稳定** | 三个默认后端都是别人的公开页面，随时可能风控/改版。这是"零成本免密钥"的固有代价。 | 已用"多后端 + 同引擎移动版回退 + 缓存 + 节流 + 风控页识别 + 手动检索入口"抬高上限；**此项属已知取舍，已在交付说明中列出** |
| 四后端同时限流时只能降级 | 实测发生过。此时产品仍能给出可点击的自助检索入口，但不返回结果 | 已实现手动检索入口（加固 5）；**未实现自动重试**——因为实测证明重试无效（见反面对照实验）。加固 6 抬高了触发阈值，**但不等于不会发生**（本机自测已把桌面版+移动版都请求到被封） |
| 搜狗 URL 为域名级 | 点进去是站点首页，非具体文章页；证据强度弱于 360 的文章级直链 | 已排在 360（桌面/移动）之后，仅作兜底 |
| Bing / 百度未接入 | 实测 Bing 中文结果会**放宽查询**（答非所问），百度只给跳转链 | **主动不接**：接入会产出"答非所问的来源"，比诚实降级更危险 |
| 解析器依赖页面结构 | 引擎改版会导致解析失效 | 已有 `tests/fixtures/` 快照 + 采集脚本，可比对定位；`_parse_*` 是纯函数，改版后只改一个函数 |
| 缓存为进程内内存 | 进程重启后缓存清空；多进程不共享 | 适用于单实例演示场景；如需多实例，可替换为 Redis（未实现） |
| 风控页识别只查标题 | 若引擎改版把风控信息只放正文，会漏判 | 漏判后果是"解析出 0 条"而非编造（因为结果结构不匹配），风险可控。**已实测复验**：见加固 7——风控改以 302 重定向出现时，跟随后的页面 4/4 被标题栏拦下 |
| 措辞敏感性的结论不够硬 | "分词串命中差、自然语句命中好"这一观察**存在混淆**（两次测量之间引擎状态在变，无法排除限流影响） | 故 `_query_variants` 只作为"顺手多试一次"，**不宣称一定能提高命中率**。如实标注，不夸大 |
