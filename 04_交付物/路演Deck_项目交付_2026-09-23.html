AI 医院资源查询与便民就医助手
真实联网 · 来源可核验 · 无法确认时如实说明

面向「昆明市民查询医院资源」这一实际场景的便民就医助手：以真实联网检索结果为回答依据，来源可点击核验，输出结构固定。本 Deck 说明这套系统的设计取舍与工程边界。

真实联网检索来源可核验 R1–R13 结构性护栏四段式结构化输出 同名消歧 / 冲突提示对比视图 / 历史 / 筛选
讲解要点：开场先交代主线：真实联网检索、来源可核验、无法确认时如实说明。本项目不做预置答案，也不以推测填补未查到的内容。
背景

便民就医信息查询的四类实际问题

信息分散

同一类资源（如抗蛇毒血清）散见于新闻报道、政府公开栏与医院官网，使用者需跨多个站点才能得到完整信息。

信息时效性

易变资源（血清库存、出诊排班）时效性强，将旧报道当作当前状态会直接误导判断。

难以核验

回答不标注来源时，使用者无法判断信息出自哪家机构、发布于何时、是否可靠。

主体混淆

同名医院存在多个院区，不同来源的表述也可能冲突，混合呈现会导致错误结论。

讲解要点：建议以「抗蛇毒血清」一个例子串联四类问题：使用者最担心的是「检索结果显示有、实际到院却没有」。其中时效性与主体混淆两项在医疗场景中的影响最大。
实现方式

真实联网检索 + 四段式结构化输出

  • 真实联网：编排层将用户问题转为检索式，实际调用搜索引擎（so360 / mso360 / sogou 同族瀑布回退 + 神马独立源），不使用预置答案。
  • 四段式契约：① 查询条件 ② 查询结果 ③ 信息依据 ④ 使用提示——结构固定、字段完备、来源必填。
  • 易变资源三态：每条资源标注「历史上有相关报道 / 公开页面介绍具备相关能力 / 目前是否可提供尚待核实」，将不确定信息显式说明。
  • 无法确认时如实说明：查不到即明确表示未查到，不补充看似合理的推测结果；未配置密钥时直接提示配置，不发起检索、也不会给出替代性答案。
讲解要点：四段式结构既是给使用者的阅读结构，也是给系统的校验契约。可强调：常见失误是「回答看似专业但缺少可核验依据」，本项目以结构性护栏加以约束（见下一页）。
关键机制 ①

结构性护栏 R1–R13

R1–R3 结构完备 / 来源必填 / 来源可达

四段式字段齐备、非空壳；每条结果必须附可核验来源 URL；可选探测链接可达性。

R4–R6 边界拒答 / 紧急优先 / 禁断言

涉诊断开药等越界请求不予答复并引导就医；紧急情况优先给出急救提示；不输出无来源支撑的确定性表述。

R7–R9 空字段标注 / 检索真实性 / 易变资源三态

无来源字段须标注未查到；声称已检索须与检索留痕一致；易变资源强制三态标注。

R10–R13 院区纪律 / 同名消歧 / 冲突提示 / 来源可追溯

不同院区信息不得混用；同名主体主动区分；来源冲突显式提示；引用链接须出自本轮检索命中集合。

讲解要点：编排层与护栏层是本项目的核心。系统以 R1–R13 的结构性与契约性校验，从架构层面排除「以预置内容冒充查询结果」的做法。演示时可展开「护栏留痕」查看打回轮数。
关键机制 ②

进阶能力

A2 同名医院与院区自动消歧

多后端返回同名机构时，逐条标注所属院区与地址，不混用信息（与 R10 呼应）。

A3 多来源冲突自动提示

同一事实在不同来源中表述不一致时，主动提示「来源间存在冲突，以官方为准」。

A4 横向对比视图

结果页的对比视图可将多家医院的同一资源并排比较；表格列由数据动态生成，不硬编码距离或坐标。

B1 历史记录 / B2 条件筛选

可回看历史会话；结果支持按类型筛选与关键词搜索，降低信息过载。

讲解要点：同名消歧与来源冲突提示依赖「真实联网多源」才会出现，静态数据的演示通常不会涉及。这两项可作为系统确实在执行多后端真实检索的旁证。
技术架构

编排层 + 护栏层 + 多后端检索

  • 编排层：串联「问题 → 检索式 → 生成 → 护栏打回」循环，包含流式进度与反射式重试。
  • 护栏层：R1–R13 作为生成后的结构性校验，不合格则打回重新组织；判据取自字段声明，不依赖推测措辞。
  • 检索独立性：so360 / mso360 / sogou 同族瀑布回退，并叠加神马（m.sm.cn）独立源——独立运营方、独立限流额度，避免同族后端被同时限流导致的伪冗余。
  • 密钥零落盘：模型密钥存放于项目外的密钥库，源码中不含任何密钥值；未配置密钥时仅提示配置，不检索、不编造。
讲解要点：重点说明「检索独立性」：同一引擎的多个入口共用限流额度，一旦被限流会同时失效；神马由独立运营方提供，限流额度独立，实测可作为可达的独立来源，用于提升取数成功率。

商业交付能力

适用对象 · 部署路径 · 成本结构 · 场景适配

适用对象

地市级卫健委 / 便民服务平台 / 医院导诊台 / 县域医共体——将「查询资源」能力接入现有便民入口。

部署路径

一键启动包（含容器化部署）；使用方自备模型密钥，源码不含密钥；可私有化部署于政务内网。

成本结构

检索使用免密钥公开来源；仅模型调用按量计费；无爬虫运维成本。边际成本随调用量线性增长，可核算。

场景适配

面向「便民就医」场景：解决信息分散、时效性与核验问题，不替代医生诊断，合规边界清晰。

讲解要点：《商业交付与落地说明》补充了落地维度：使用方通常是平台方而非个人使用者；部署形态为「接入口 + 自备密钥」；成本结构为「检索免费、模型按量计费」。要点是可落地、可核算。
现场演示动线

4 分钟演示流程（建议顺序）

  • ① 提问「昆明哪家医院有抗蛇毒血清？」→ 查看检索过程留痕与三态标注。
  • ② 打开「对比视图」→ 多家医院并排比较，来源可点击。
  • ③ 提问一个多来源存在冲突的问题 → 查看冲突提示「以官方为准」。
  • ④ 提问一个条件不完整的问题（如「帮我找专家」而未给科室）→ 查看澄清轮不检索、追问所需条件。
  • ⑤ 打开「历史记录」→ 回看刚才的会话，验证多轮承接。
讲解要点：演示顺序为「真实检索 → 如实说明 → 进阶能力 → 条件澄清 → 历史会话」，与 Deck 主线一致。重点是让观看者看到检索过程与护栏留痕在运行，而非只看静态结果。条件澄清一轮可体现判定由字段驱动，而非固定话术。
设计取舍与边界

设计取舍与工程边界

  • 真实检索 + 无法确认时如实说明：查不到即明确说明，不给出看似合理但无依据的结论。医疗场景下这是必要前提。
  • 架构级约束：R1–R13 将可核验要求写入校验逻辑，而非仅依赖提示词约束。
  • 检索独立性：引入独立运营的检索来源，提升生产环境下真实检索的稳定性。
  • 待补充项：本机 IP 受限流影响的部分真机截图仍在补拍（代码无需改动）。系统不会把无法访问的页面当作可用来源。
讲解要点：收尾回到主线：本项目的重点在于回答的可核验性与边界说明的完整性，而非表达的完整流畅。真机截图一项为唯一待补充内容，如实说明即可。
