## 四、「真直连」断言的两层设计与三态判定（本轮升级要点）

**背景**：本机/使用者的机器可能残留 `HTTP(S)_PROXY` 或 VPN 出口。若不显式直连，检索请求会被引擎当机器流量风控（拿到「HTTP 200 却是验证页」）、模型调用会超时、启动器的就绪探测会误判超时——最后表现为**双击后浏览器根本打不开**。故三处外呼（检索 / 模型 / 启动器探测）都必须真直连，且必须有**骗不过的护栏**。

**第一层（辅助判据，静态三相）**：拦截 `httpx.Client.__init__`（所有外呼路径的**收敛点**），核**全部**外呼记录都满足「`trust_env is False` ∧ 无显式 `proxy` ∧ 无自定义 `mounts`」。

> ⚠️ 这一层**不完备**，实测确认有第四维：`transport=HTTPTransport(proxy=死代理)` 时三相**全绿**，而请求实际走代理。httpx 0.28.1 会改出口的路由参数穷举为 4 个（`trust_env` / `proxy` / `mounts` / `transport`），将来还可能增加——**枚举永远追不上**，故它只作辅助。

**第二层（主判据，收敛式连通性活体探针）**：起一个本机 HTTP 靶子服务 + 把环境代理指向**必然连不上的死地址**，直接看被测对象**能不能连上**。它**不枚举任何参数**——凡是让请求绕道的写法（含第四维、以及将来的暗门）都会在"到底连不连得上"上暴露。属性可以被设成想要的值，**连通性不能**。

**三态判定（防"探针恒真"）**：活体探针依赖"本环境对回环地址没有隐式放行"。若机器设了 `NO_PROXY=127.0.0.1`（或 Windows 注册表 `ProxyOverride` 含 `<local>`），**连默认会走代理的客户端也能连上本机服务** → 探针恒真、失去鉴别力。故每条探针都带**两条被断言的对照臂**：

1. 对照臂 A＝默认会读环境代理的客户端；2. 对照臂 B＝显式指向死代理的客户端。

| 对照臂情形 | 判定 |
| ---------- | ---- |
| A、B **都连不上** | 代理道全断 → 活体判据**全维度有效** → 以被测对象的连通性定 PASS / FAIL |
| **任一条能连上** | 该道被放行、活体判据**无鉴别力** → **不判绿**，改读**环境无关**判据（已解析传输层的代理痕迹）：无痕迹 = PASS，有痕迹 = FAIL，**读不到 = INCONCLUSIVE** |

`INCONCLUSIVE`（取不到证）**明确不算绿**——宁可不给结论，也不给假绿。

**第四轮对抗验证（4/4 达预期）**：

| 变异 | 期望 | 结果 |
| ---- | ---- | ---- |
| `search._get` 用 `transport=` 死代理（第四维） | 变红 | ✅ 97/98（**静态三相仍判绿**，靠活体探针抓出） |
| 模型直连工厂用 `transport=` 死代理（第四维） | 变红 | ✅ 97/98（同上） |
| `search._get` 正确重构为 `Client(trust_env=False)` | **保持绿** | ✅ 98/98（无假红） |
| 模型直连工厂正确重构为 `transport=干净 HTTPTransport()` | **保持绿** | ✅ 98/98（无假红） |
