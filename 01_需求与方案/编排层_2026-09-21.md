# 编排层设计说明

> 作品名称：AI 医院资源查询与便民就医助手
> 对应接口版本：`api_version = 1.0` ｜ 文档版本：2026-09-24

---

## 一、设计背景与核心约束

本作品需要回答的是「医院、科室、医生、出诊、特殊资源」这类事实性就医信息。这类信息变化快、来源分散，且一旦出错会直接影响使用者判断，因此编排层的设计围绕以下约束展开。

### 1.1 赛题给定的实现约束

- 基础功能必须包含**真实联网检索**，以及对用户请求的**动态处理**；
- **不得通过硬编码医院答案或预设对话**冒充动态查询；
- 规则可用于**参数校验、模板呈现和边界控制**，但不得通过硬编码事实冒充动态查询。

### 1.2 由此推导出的三条设计结论

| 结论 | 含义 |
|---|---|
| 必须采用 Agent 编排 | 由模型担任控制器，代码提供工具、原则、输出契约与允许的轻量规则 |
| 事实一律不可硬编码 | 任何医院名、科室名、医生名、排班、号源、资源结论，只能来自真实检索来源 |
| 规则、边界、校验可以写入代码 | 参数校验、边界触发、输出结构、来源对账属确定性逻辑，适合由代码保证 |

> 反过来说：若代码去替模型判断「某医院是否真有某科室」，模型将失去推理空间，且系统会退化为预设答案的查找表——这正是本作品明确避免的形态。

## 二、编排层结构（四层）

### 2.1 原则层（写入系统提示词的判断原则，而非规则树）

- **角色**：医院资源查询与便民就医助手。
- **主动联网检索**：不以模型内部记忆回答医院事实。
- **来源可核验**：权威渠道（医院官网 / 官方公开页 / 卫健委）优先；补充来源须注明性质与核验情况，**不把搜索摘要直接当作已核实事实**。
- **不编造**：查不到时标注「未查到 / 待核实」；**不作出「该医院没有该科室 / 医生 / 资源」这类断言**。
- **区分三态（关键呈现方式）**：`历史上有相关报道` / `公开页面介绍具备相关能力` / `目前是否可提供尚待核实`。特殊资源（如抗蛇毒血清）必须标注，不得将历史储备、采购或救治报道等同于当前库存或可立即使用。
- **边界拒答**：不诊断、不治疗、不用药、不提供处方指导；遇紧急求助**优先提示联系当地急救（120）**，不以继续检索替代。
- **时效说明**：不将抓取日期当作更新日期；来源未标注日期时写明「**来源未标注更新时间**」。
- **院区纪律**：医院有多个院区时，每条结果标明**适用院区**（地址、科室、医生、出诊排班分别属于哪个院区）；不同院区的信息不得混用，也不得合并为一条；来源未标明的写明「来源未标明院区」，**不得自行推定**。
- **条件澄清**：需要查询医院 / 科室 / 医生 / 资源但**未说明地区**、且同一会话上文也无线索时，**不检索、不推定地区**，先询问用户所在城市或地区，待用户补充后再检索。**演示范围不得替代用户给出的条件**。

### 2.2 能力层（工具，模型按需调用）

| 工具 | 说明 |
|---|---|
| `search(查询词, 城市)` | 真实联网检索，返回 `标题 / 链接 / 摘要 / 来源性质（权威｜补充）` |
| `fetch(url)` | 获取网页正文（遵守访问规则，不绕过登录或权限限制） |
| `session(读/写/重置)` | 多轮上下文、会话隔离、会话重置 |
| `retrieval_log` | 每次 `search` / `fetch` 的 `查询词 / 调用状态 / 返回来源` 留痕，供前端实时展示，同时作为来源可追溯校验的依据 |

`retrieval_log` 作为一等数据结构存在：它既是前端「检索过程可见」的数据来源，也是护栏层核验「模型引用的来源是否真的来自本轮检索」的唯一依据。

### 2.3 控制循环（由模型驱动）

```
理解意图
  → 判断缺失条件是否影响检索
      · 不影响 → 直接按演示范围检索
      · 影响   → 先澄清（模型显式声明 need_clarification 字段）
  → 调用工具（search / fetch）
  → 从来源提取事实，关联链接 + 时间 + 来源性质
  → 冲突信息标出
  → 按四段式契约产出
  → 多轮承接
```

**关于条件澄清的实现方式**：早期版本曾用固定词表推测用户或模型的措辞，并在命中时输出固定的追问话术。该方式存在两个问题：措辞变化维度大，词表必然遗漏；且本项目演示范围固定为昆明，追问城市对多数查询并无必要。

现行实现改为**由模型判断、以字段声明**：地区作为固定事实注入，无需追问；当缺失科室、医院、资源等真实条件时，由模型自行判断并在输出 JSON 顶层**显式声明 `need_clarification` 字段**，编排层读取该字段决定是否进入澄清轮，不推测措辞。

### 2.4 护栏层（反射式校验打回循环 · Reflection Guardrail Loop）

模型产出结果后，代码执行**结构性与契约性校验**（只检查「左侧」规则，不检查事实真假）。校验不通过时，将**违规点与修正提示编码后回灌给模型**，由模型重新组织语言输出，形成「生成 → 校验 → 打回 → 再生成」的循环。**模型始终是控制器，代码只提供校验与提示，不替模型写事实、不预设对话内容。**

#### 2.4.1 静态标注（兜底）

每条事实性陈述须带来源链接与性质；出诊信息受硬约束；框架填充受禁止。校验不通过时在输出内标注。该项仅作兜底。

#### 2.4.2 主动打回循环

| 组件 | 职责 |
|---|---|
| `Validator` | 输入模型响应（四段式 schema），输出 `{ pass, violations[{rule, field, detail}], hints[] }`。规则集见 2.4.3 |
| `Reflector` | `pass == false` 时，将 `violations + hints` 拼装为**结构化反思指令**回灌至 messages，模型携带约束重新生成。反馈措辞由代码生成、执行由模型完成——**不是重新检索，而是重新组织语言** |
| `Loop Controller` | 最多打回 **N = 2 轮**；每轮写入 `retrieval_log`（透明留痕，如「护栏打回 ×k：缺来源 / 越界」）；超过 N 轮则**降级输出**并附「⚠️ 未完全满足全部约束」提示，仍交付、不崩溃、不卡死 |

#### 2.4.3 Validator 规则集

以下规则全部位于「左侧」，即代码可以写入的确定性逻辑：

| 规则 | 名称 | 判据 | 处置 |
|---|---|---|---|
| R1 | 结构完备 | 四段式字段齐全、非空壳 | 打回 |
| R2 | 来源必填 | 每条结果必须带 `source(title + url)`，url 合法且为 http(s) | 打回 |
| R3 | 来源可达 | 可选规则：对 url 做轻量可达性探测；不可达则提示换源或标待核实 | 打回 |
| R4 | 边界拒答 | 用户询问诊断 / 用药 / 治疗时，响应不得含诊断结论或用药建议 | 打回 |
| R5 | 紧急优先 | 检出紧急词（胸痛 / 昏迷 / 大出血 / 轻生倾向等）时，响应必须含「请立即拨打 120」 | 打回 |
| R6 | 禁断言 | 不得出现「目前可提供 / 有号 / 可预约成功 / 确定出诊」等无检索支撑的断言 | 打回 |
| R7 | 空字段诚实 | 无来源字段须标注「未查到 / 待核实」，不得留空或编造 | 打回 |
| R8 | 检索真实性 | 响应声称「已检索」须与 `retrieval_log` 一致，防止谎称检索 | 打回 |
| R9 | 易变资源三态 | 用户查询血清 / 血库 / 床位 / 号源等易变资源时，每条结果须标注 `info_status` 三态之一 | 打回 |
| R10 | 院区纪律 | 用户提及院区（命中通用院区词）时，每条结果须标明**适用院区**（`campus` 字段，或在名称 / 说明中写清） | 打回 |
| R11 | 同名消歧一致性 | 存在同名但非同一主体的机构时，须明确区分，不得混用信息 | 打回 |
| R12 | 冲突提示 | 不同来源对同一事实表述不一致时，须显式标出冲突，不得择一静默呈现 | 打回 |
| R13 | 来源可追溯 | 模型引用的每条来源链接（含 `query_results[].source.url` 与 `info_basis[].url` 两处）必须出自本轮检索命中集合（由 `retrieval_log` 与多轮白名单共同构成） | 打回 |

**澄清轮豁免（`clarify=True`）**：R1 与 R7 在**条件澄清轮**豁免——澄清轮本身就没有条件与结果，属于预期状态。**但不豁免编造**：澄清轮若塞入结果，仍由 R8 打回。

> **Validator 的硬边界**：上述规则只校验**结构、契约与边界词触发**，**不判断事实真假**（例如「昆医附一院是否真有心血管内科」）。事实真假只能通过来源链接与人工核验确认。越过这条边界即等于由代码判定事实，超出本层职责。

#### 2.4.4 打回反馈格式（代码生成，模型执行）

```
【护栏拦截·第 2 轮】检测到违规：
① 第 2 条结果未附来源链接（R2）；
② 你写了"该院目前有号"（R6，违反出诊硬约束）。
请：(a) 为该结果补上可核验的官方来源链接，或 (b) 改为"暂未查到可核验的出诊安排"。
重新组织语言后输出，勿编造。
```

## 三、代码层职责边界

赛题明确「规则可用于参数校验、模板呈现和边界控制」。据此划定代码层的书写边界：

| 代码层可以写入 | 代码层禁止写入 |
|---|---|
| 参数校验：空输入 / 超长 / 格式 / 超时判定 | 任何具体医院名、科室名、医生名 |
| 边界触发词：诊断 / 用药 / 紧急 → 提示模型拒答或提示 120 | 任何出诊排班、号源、擅长领域等事实 |
| 模板：四段式输出结构、字段形状 | 任何预设对话或对答脚本 |
| 来源性质标注逻辑（权威 / 补充判定词表） | 任何「某医院有某资源」的结论 |
| 检索失败与异常的统一提示文案 | 任何硬编码的检索结果 |
| Validator 校验规则（结构 / 契约 / 边界词触发，属左侧） | Validator 校验事实真假（属右侧，见 §2.4.3 硬边界） |

> 一句话概括：**代码只承载规则、边界与校验；事实全部由模型从真实检索来源产出。**

## 四、输出契约（四段式）

输出契约由代码定义 schema，模型从真实来源填充内容，渲染层据此输出卡片或表格：

```
{
  查询条件: {地区, 医院/院区, 资源/科室, 医生条件, 查询日期},
  查询结果: [{
    医院全称, 院区, 类别, 匹配资源, 匹配依据,
    信息状态: 历史报道 | 公开介绍具备能力 | 目前可提供尚待核实,
    涉及医生: [{姓名, 科室, 职称, 擅长领域(忠实概括),
                出诊: {类型: 周期|排班, 院区, 日期/周期, 来源时间}}],
    来源: {标题, 链接, 来源性质: 权威|补充, 更新时间(如有), 查询时间}
  }],
  信息依据: [来源明细],
  使用提示: [未核实 / 过期 / 冲突说明, 官方核实或预约方式]
}
检索过程: retrieval_log[]   // 独立展示，不混入答案
```

代码负责结构、来源必填、三态枚举与禁止框架填充；**不承载任何具体事实**。

## 五、与赛题需求的对应关系

| 需求方向 | 编排层的实现方式 |
|---|---|
| 主动搜索与来源核验 | `search` 工具 + 来源必填（R2）+ 来源性质标注 + `retrieval_log` 前端展示 + 冲突提示（R12） |
| 医院资源整理 | 结果按院区隔离（R10）；信息状态三态字段（R9）；演示城市固定为昆明 |
| 科室与医生 | 信息提取 + 出诊区分固定周期与某日排班；出诊硬约束（R6）；不作疗效承诺、不做无依据排名 |
| 多轮对话与便民问答 | `session` 工具 + 边界清单（费用 / 医保 / 交通 / 办理条件在无来源时不自行补齐） |
| 四段式输出框架 | schema 强制 + 反射式打回（R1 / R7 等） |
| 小程序接入 | REST 接口返回 schema；接入范围明确标注为模拟调用 |
| 交付物与可运行性 | 输入护栏（空 / 超长 / 越域 / 超时 / 检索失败提示与重试）+ 检索中状态展示 + 8 组测试场景 |
| 检索质量与更新提醒 | 多权威来源交叉核验、同名机构消歧（R11）、冲突提示（R12）、易变信息过期提醒 |
| 交互与结果比较 | 移动端适配、常用问题入口、条件筛选、医院比较（围绕地区 / 院区 / 资源，不以医疗质量排名替代） |
| 会话持久化与运行保障 | 历史会话查看与清除、限流、缓存更新、失败重试、成本记录、降级方式说明 |
| 小程序实际集成 | 提供接入说明与模拟调用页；真实集成需自有或授权测试小程序 |

## 六、实现现状与设计取舍

| 项目 | 现状 |
|---|---|
| 输入护栏 | 已实现：空输入、超长（> 500 字）、越域、超时、检索失败，均有统一提示 |
| 检索过程可观测 | 已实现：`retrieval_log` 实时渲染「检索词 → 调用中 → 返回 N 条来源（权威/补充）」，并在回答产出后自动收拢 |
| 来源性质标注 | 已实现：`source_type: 权威｜补充` + 核验状态；补充来源明示「未经官方核实」 |
| 出诊硬约束 | 已实现：无来源日期的出诊陈述、由往期推断当前号源或预约成功的表述一律拦截，改写为「暂未查到可核验的出诊安排」并引导官方挂号 |
| 三态信息状态 | 已实现：特殊资源强制标注三态之一 |
| 交叉核验与消歧 | 已实现：同名机构消歧（R11）、来源冲突提示（R12） |
| 检索层能力边界 | 当前检索层只取搜索结果的标题 / 摘要 / 链接，不解析网页正文；`fetch` 工具已预留，未启用正文抓取 |
| 会话持久化 | 当前为进程内内存实现，未接入数据库或 Redis；适合单实例演示场景，如需多实例需替换存储层 |
